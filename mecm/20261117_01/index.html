ハードウェア インベントリについての動作説明

皆様、こんにちは。Configuration Manager / WSUS サポート チームです。

本記事では、Configuration Manager のハードウェア インベントリについて、クライアントで収集が起動されてから、管理ポイントを経由してサイト データベースへ取り込まれるまでの動作とログの追跡方法をご案内します。全件更新と差分更新の違いも、同じクライアントのログを用いて説明します。

全体の流れ

  1. スケジュールまたは手動操作で収集サイクルを起動する
  2. レポートの種類を決定し、対象の情報を収集する
  3. インベントリ レポート (.xml ファイル) を生成し、送信を要求する
  4. クライアントから管理ポイントへレポートを配送する
  5. 管理ポイントでクライアントから届いた xml ファイルを MIF ファイルに変換し、サイトへ引き渡す
  6. サイト サーバーでサイト データベースへ取り込む

動作説明の前提

ハードウェア インベントリは、クライアント設定で有効にし、収集スケジュールと収集対象のクラス・属性を設定して使用します。設定を変更した場合は、クライアントがポリシーを取得してから収集に反映されます。

全件更新と差分更新では、サイトへ報告する情報の範囲が異なります。

種類 報告する内容 ログで確認する点
全件更新 端末上のあらゆる情報ではなく、収集対象として設定された範囲の情報全体を報告します。 初回の Full や、再同期時の ReSync といったレポートの種類を確認します。
差分更新 前回の収集結果からの変更を報告します。 Delta とレポート バージョンを確認します。

クライアントが最初に返すインベントリは全件で、その後は差分を返します。差分が欠落した場合、サイトは後続の差分を拒否し、クライアントへ全件収集を要求します。詳細は ハードウェア インベントリの概要 をご参照ください。

収集サイクルを手動で実行した場合も、クライアントの収集状態に応じて全件更新または差分更新が行われます。本記事の全件更新の例では、以下の PowerShell を使用して全件収集を強制的に実行しています。

注意

対象の Configuration Manager クライアント上で、Windows PowerShell 5.1 を管理者として起動して実行します。
使用している WMI コマンドレットは PowerShell 7 では削除されているため、PowerShell 7 では実行できません。

1 行目では、前回の収集日時やレポート バージョンを保持する InventoryActionStatus クラス から、ハードウェア インベントリに対応する状態を削除します。2 行目では、収集サイクルを起動します。この全件収集の要求方法は、関連記事 ハードウェア インベントリ情報が採取されない場合のトラブルシューティング でもご案内していますので、ご確認ください。

差分更新の例では、その後、同じクライアントで収集サイクルを再度手動実行しています。収集サイクルを起動するだけの場合は 2 行目を実行し、全件収集を要求するための 1 行目の状態削除は行いません。

以下では、管理ポイントをプライマリ サイト サーバーと同じサーバーに配置した構成で、サイト データベースへの取り込みを追跡します。セカンダリ サイト経由の MIF 転送は対象外ですので、ご留意ください。

各ステップとログの追跡方法

関連ログ

ログ名 保存場所 主な用途
Scheduler.log クライアントの C:\Windows\CCM\Logs 定期スケジュールからの収集起動を確認します。
smscliui.log クライアントの C:\Windows\CCM\Logs クライアントの収集サイクルを実行した操作を確認します。
InventoryAgent.log クライアントの C:\Windows\CCM\Logs レポートの種類、情報の収集、レポート生成、送信要求を確認します。
CcmMessaging.log クライアントの C:\Windows\CCM\Logs 管理ポイントへの実際の配送結果を確認します。
MP_Hinv.log 管理ポイントのログ フォルダー レポートの受信情報と MIF への変換を確認します。
mpfdm.log 管理ポイントのログ フォルダー クライアント ファイルをサイト サーバーへ引き渡す処理と、格納先の INBOXES フォルダーとの対応関係を確認します。
dataldr.log サイト サーバーの <Configuration Manager インストール先>\Logs MIF の処理とサイト データベースへの取り込みを確認します。

管理ポイントのログ フォルダーは、例えば C:\SMS_CCM\Logs です。役割の配置やインストール先によって異なるため、対象サーバー上の保存先をご確認ください。ログの役割は ログ ファイルのリファレンス でも確認できます。

ログ間の対応付け

同じ端末から複数回のレポートが届くため、端末名だけでなく、レポート バージョン、メッセージ ID、および MIF ファイル名を組み合わせて追跡します。

対象クライアント CLIENT01 CLIENT01
クライアント GUID 631942E3-EC38-4623-8D15-22BFD5C175C5 631942E3-EC38-4623-8D15-22BFD5C175C5
レポートの種類とバージョン ReSync、3.0 Delta、3.1
送信メッセージ ID BC93BDBF-4295-4680-923F-37A910A7D869 B04B4837-A7AD-4DF1-A013-604D40BEFF69
MIF ファイル名 HDUMCY0A.MIF H31MBSZJ.MIF

InventoryAgent.log と CcmMessaging.log は送信メッセージ ID で照合します。MP_Hinv.log の受信レポート情報でクライアント GUID、レポートの種類とバージョンを確認し、変換後の MIF ファイル名で dataldr.log へ追跡します。mpfdm.log では、ハードウェア インベントリの格納先フォルダーとの対応関係を確認します。ログごとに出力される識別情報が異なりますので、それぞれの確認項目を使い分けてご確認ください。

以下のログはメッセージ本文を抜粋し、行ごとの日時などの付帯情報を除外しています。端末名とサーバー名は匿名化し、途中の行を省略した箇所は「中略」と示しています。Scheduler.log の定期起動例は、全件更新 (3.0) および差分更新 (3.1) の手動起動とは別の収集サイクルです。

ステップ 2 : レポートの種類を決定し、対象の情報を収集する

InventoryAgent.log では、Action=Hardware の行でハードウェア インベントリであることと、レポートの種類を確認します。このログにはソフトウェア インベントリやハートビート探索も記録されるため、Action=Hardware と ReportType を組み合わせて対象の収集サイクルを識別します。

PowerShell で全件収集を要求した今回の例では、バージョン不一致を検出し、全件レポートを生成することが記録されています。直後の種類は ReSync、バージョンは 3.0 です。

中略

この例の ReSync は全件の再同期レポートです。初回収集の Full という表記だけでなく、前後のメッセージと、ステップ 6 のサイト側の扱いまで確認することで、全件更新であることを追跡できます。

続く差分更新では、同じメジャー バージョンのままマイナー バージョンが進み、Delta、3.1 になっています。

クライアントは、設定された収集対象に対して情報を取得します。例えば、差分更新でも次のような WMI クエリの実行が記録されています。

差分更新でも収集対象のクラスから情報を取得し、前回の収集結果との差分をレポートにまとめます。必要な情報が含まれない場合は、対象クラスの収集設定と、そのクラスに対応するクエリの前後のメッセージをご確認ください。

収集後、クライアントはレポートを生成します。InventoryAgent.log では、生成したエントリ数と、宛先 MP_HinvEndpoint への送信要求を確認します。

この例では、同じ収集対象に対して全件側は 1,583 エントリ、差分側は 10 エントリを報告しています。エントリ数は端末の情報や変更内容によって異なりますので、変更した属性の数そのものではなく、レポートにまとめられたエントリの数としてご確認ください。

Successfully sent report は InventoryAgent 側の送信処理を確認するメッセージです。管理ポイントへの配送完了やサイト データベースへの取り込み完了は、次のステップ以降で確認します。レポートが生成されない場合は、同じ収集サイクル内の収集結果とレポート生成時のエラーを確認します。

ステップ 4 : クライアントから管理ポイントへレポートを配送する

CcmMessaging.log を、ステップ 3 のメッセージ ID で検索します。全件更新では、管理ポイントへの配送成功が次のように記録されています。

差分更新も、同じく送信メッセージ ID で確認できます。

Delivered successfully により、対象メッセージの管理ポイントへの配送成功を確認できます。サイト データベースへの取り込み結果は、続くサーバー側のログでご確認ください。

配送成功が確認できない場合は、同じ ID の再試行や通信エラーの記録を追跡します。InventoryAgent.log の送信メッセージと対応させることで、別の種類のクライアント通信との混同を避けられます。

ステップ 5 : 管理ポイントで MIF ファイルに変換し、サイトへ引き渡す

管理ポイントはクライアントから受信した XML 形式のハードウェア インベントリを、サイトで処理する MIF (Management Information Format) ファイルへ変換します。MP_Hinv.log の受信レポート情報では、ClientID、NetBIOSName、ReportType、および Version を確認します。

掲載例では、同じクライアント GUID に対して Resync の 3.0 と Delta の 3.1 が記録され、それぞれ次の MIF ファイルへの変換成功を確認できます。

差分更新の例です。

管理ポイントからサイト サーバーへのファイルの引き渡しは、mpfdm.log で確認します。掲載例のように管理ポイントとサイト サーバーが同じサーバーにある構成では、mpfdm.log に次の格納先の情報が記録されています。

中略

Data Loader (Trusted) の行から、ハードウェア インベントリの hinv.box と、サイト サーバーの格納先である E:\ConfigMgr\inboxes\auth\dataldr.box の対応関係を確認できます。この格納先は、先ほどの MP_Hinv.log に記録された MIF ファイルの出力先と一致しています。

ここでは、mpfdm.log で格納先の対応関係を確認し、個々の MIF ファイルの生成と取り込みは MP_Hinv.log と dataldr.log で追跡します。管理ポイントが別のサーバーにある場合は、mpfdm.log の転送処理も併せてご確認ください。

変換成功を確認した後は、MIF ファイル名を使って dataldr.log を検索します。変換に失敗している場合は、MP_Hinv.log の対象レポートを処理した箇所でエラーを確認します。

ステップ 6 : サイト サーバーでサイト データベースへ取り込む

サイト サーバーの Inventory Data Loader は、MIF ファイルを処理してサイト データベースへ情報を取り込みます。dataldr.log では、ファイル名で処理開始箇所を見つけ、クライアント GUID を確認しながら追跡します。

差分側も同じクライアントの取り込み成功を確認できます。処理完了行では、ここに示すように MIF 名の先頭に X が付いた名前が記録されています。

取り込みが確認できない場合は、dataldr.log の対象 MIF に対するエラーや拒否の記録を確認します。差分欠落時の全件要求と、通信やファイル変換の失敗を区別して、処理が止まっている工程を絞り込みます。全件収集の実行方法を含む確認手順は、関連記事 ハードウェア インベントリ情報が採取されない場合のトラブルシューティング もご参照ください。

このように、起動記録、InventoryAgent.log のレポート種類と送信 ID、CcmMessaging.log の配送結果、MP_Hinv.log の MIF ファイル名、dataldr.log の取り込み結果を順に確認すると、クライアントからサイト データベースまでを追跡できます。
